# 性能基线（实测 · 2026-09-12）

> 全部数字来自**实测**，可用 `scripts/bench_scale.py` 与 `scripts/bench_concurrency.py` 复现。
> 本机环境：Windows 11 · SQLite（单文件） · 单进程 · Python 3.14（.venv）。
> **这些不是分布式/列存引擎的容量数字**，只用于横向对比与发现瓶颈。

## 1. 规模（行数）

`python scripts/bench_scale.py --rows N`（9 列事实表 + 20 行维表）

| 场景 | 20 万行 | 100 万行 | 放大（×5 行数） |
|---|---|---|---|
| 全表聚合 COUNT/SUM | 55 ms | 94 ms | 1.7×（有索引/缓存效应） |
| 分组聚合（20 组） | 145 ms | 723 ms | 5.0× |
| 明细 LIMIT 100 | — | 5.4 ms | 与规模无关 |
| JOIN 维表聚合 | — | 377 ms | 线性 |
| **`dataset_profile`（9 列）** | **401 ms** | **2043 ms** | **5.1×** |
| 业务语义采集（维表取值） | 3 ms | 3 ms | **与规模无关**（有界查询，设计如此） |

### 结论（可直接用于面试/评审）
1. **`dataset_profile` 是唯一随规模线性恶化且最慢的一步**：≈ 0.4 ms/(行·列) × 列数。
   - 9 列 × 100 万行 = **2.0s**；外推 **100 列宽表 × 100 万行 ≈ 22s**；**1 亿行 ≈ 不可用**。
   - 原因：逐列 `COUNT(DISTINCT)` 各扫一遍全表（E4/01 的实现选择，换来的是跨方言安全与确定性）。
   - **改进方向（按性价比）**：① 只画像被引用到的列（planner 已知维度）；② 行数超阈值改**采样**估计；
     ③ 高基数列用近似去重（HLL）。**建议在接入真实宽表前先做 ①。**
2. 明细查询与语义采集**不随规模恶化**，符合设计（`LIMIT` 与有界窗口）。
3. `sql_max_rows=5000` 生效中，明细类查询不会把大表拉进上下文。

## 2. 并发（`/chat/analyze`，mock 模式）

`python scripts/bench_concurrency.py --concurrency 8 --requests 40 [--workers N]`

| 配置 | 总耗时 | 吞吐 | 成功率 | P50 | P95 | P99 | 缓存命中 |
|---|---|---|---|---|---|---|---|
| 工具并行 workers=4（默认） | **7.21 s** | **5.54 req/s** | **1.00** | 77.7 ms | 3773 ms | 3780 ms | 60% |
| 工具并行 workers=1 | 8.01 s | 5.00 req/s | 1.00 | 62.8 ms | 4742 ms | 4746 ms | 60% |

### 结论
1. **8 并发 × 40 请求零失败**，无死锁、无状态串扰（每线程独立 client + 独立会话）。
2. **延迟是双峰的**：P50 78 ms（缓存命中，整条链 0 次 LLM 调用）vs P95 3.8 s（真跑一遍）。
   → 缓存对**重复提问**的收益是 48 倍，这也是"分析师反复问同一个问题"场景的真实改善。
3. **工具并行的实测收益有限**（wall −10%、P95 −20%），因为 mock 模式下耗时由 LLM 阶段主导（~3.8s），
   工具（SQLite 毫秒级）不是瓶颈。**真实业务库 + 慢查询下收益应更大，但未实测，不作声称。**
4. 本机单进程；生产容量需在目标部署形态（多 worker / 容器）下复测——**测试即脚本，可复跑**。

## 3. 未测（如实标注）
- 多进程/多副本（uvicorn workers、容器横向扩展）下的吞吐与 Redis/PG 竞争。
- 真实业务库（PostgreSQL/MySQL 百万级宽表）的查询耗时。
- 真实模型下的端到端 P95（受上游限流影响，波动大；见 `eval-real-baseline.md`）。
- 长时间稳定性（内存增长、连接池耗尽）。
