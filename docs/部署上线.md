# Enterprise Data Analyst Agent · 部署与可视化上线指南

本服务是**自研编排 + 真实工具执行**的 Agent，对外是普通 FastAPI 服务，可像任何后端一样部署；另带一个**可视化控制台**（`/ui`）用于直接看多阶段分析过程，无需前端工程。

---

## 0. 对外接口一览

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/health` | 存活检查（配置意图 `llm_mode` + **观测事实** `llm_degraded/llm_fallbacks_total`） |
| GET | `/api/v1/health/llm` | 主动探测 LLM 可达性（1 token，不降级；回答「端点可达」，不回答「跑得动」） |
| POST | `/api/v1/chat/analyze` | 一次性分析，返回 JSON（含 report/findings/tool_results/reflection） |
| POST | `/api/v1/chat/analyze/stream` | SSE 流，每阶段一个事件（UI 用） |
| GET | `/ui` | **可视化控制台**（调上面的 stream） |
| POST | `/api/v1/documents/ingest` | 知识入库（`{text|file_path, source}`） |
| GET | `/api/v1/debug/traces[/{session}]` | 结构化 span / 运行回放 |

快速试跑（不需要容器，仓库内）：

```bash
MOCK_LLM=true python -m uvicorn app.main:app --port 8000
# 打开 http://127.0.0.1:8000/ui
```

## 1. 本地/内网 · 单容器最小上线

```bash
# 1) 配置：复制模板 → 填 LLM
cp .env.prod.example .env          # 填 LLM_API_KEY / LLM_BASE_URL / LLM_MODEL
# 2) 构建 + 运行（内部先跑一遍真库冒烟）
bash scripts/run-container.sh
# 3) 打开
#    控制台   http://<host>:8000/ui
#    健康     http://<host>:8000/api/v1/health
```

### 1.1 数据与状态如何持久化

- 镜像内已预生成样例库 `data/sample_enterprise.db`；运行脚本把宿主 `./data` 挂到容器 `/app/data`，`knowledge.db / long_term.jsonl / traces/ / audit/ / checkpoints/` 都会落卷，重启不丢。
- 只依赖这一个卷即可；**不配 Redis/PG/Milvus 也能跑**（自动降级：内存短记/JSONL 长记/SQLite 向量）。
- 要接真实企业库：把 `.env` 的 `DATA_DB_URL`/`DATA_DB_DIALECT` 指向目标 PG/MySQL（Agent 查询真实业务数据，只读白名单+行数/超时保护默认开启）。

### 1.2 python_analysis 沙箱在容器里怎么跑

- 镜像已装 pandas/numpy/matplotlib，默认 `PYTHON_SANDBOX_MODE=subprocess`：容器内再用隔离子进程执行分析脚本，**开箱即用**。
- `docker` 档需要把宿主 docker.sock 挂进容器再给镜像，**不建议**在单容器上线默认开；要更强隔离请用"app + 沙箱执行器"双容器。

## 2. 真实模型上线（而不是 Mock）

`MOCK_LLM=false` + 填好 key 即真实分析。两点必须注意：

1. **不要静默降级**：真实上线设 `LLM_NO_FALLBACK=true`。否则上游超时/欠费会被静默降级成 Mock，返回"假分析"而调用方不知道——本仓库的防假绿测试就是防这个。
   - 即使不改 `LLM_NO_FALLBACK`，降级现在也**对外可见**（D18 修复）：响应带 `degraded` + `llm_fallbacks[]`，SSE 事件带 `degraded`，`/health` 带观测字段。**不要只看 `mock_llm`（那是配置值）。**
   - ⚠ **「可达」不等于「跑得动」**：`/health/llm` 探测用 1 token（在余额内即返回 `reachable:true`），而流水线按 `LLM_MAX_TOKENS` 请求——余额只够 1798 时，2048 的请求会全量 402 并降级。判「真能干活」请看 `/health` 的 `llm_degraded` / `llm_fallbacks_total`。
2. **成本配额**：OpenRouter 等余额不足时会 `402`（例如"可负担 1049 tokens，请求 2048"）。对策任选：
   - 充值 / 提额度；或
   - 调低 `LLM_MAX_TOKENS`（如 900）适配当前余额（长报告可能被截断，非首选）；
   - 配 `cost_input/output_per_mtok` 后跑 `python -m app.eval.runner --mode real` 观察真实成本，再设预算告警。

验证真实链路：`python -m app.eval.runner --mode real`（golden 5 条 + 工具轨迹断言 + 真 token/成本）。

## 3. 云端上线（服务器）

以任意云主机（需公网 IP）为例：

```bash
# 服务器上
git clone <你的仓库> && cd <repo>
cp .env.prod.example .env           # 填真实 LLM、DATA_DB、是否接中间件
bash scripts/run-container.sh
```

- **入口**：建议前面加 Nginx/Caddy（HTTPS + 反代 8000）。示例 Caddy：
  ```caddyfile
  example.com {
      reverse_proxy 127.0.0.1:8000
  }
  ```
- **鉴权**：服务本身无登录。公网暴露 `/api/v1/chat/analyze` 前，务必在反代加 Basic Auth / OIDC / API Key 白名单；`/api/v1/debug/traces` 含内部运行细节，更应只在内网访问。
- **水平扩展**：无状态请求→ 多副本 + 负载均衡即可；会话记忆若用 JSONL/内存只在单副本内有效——要跨副本请启用 Redis(`REDIS_URL`) + PG(`POSTGRES_DSN`) + Milvus(`MILVUS_HOST`)。启用后重启并跑 `*_live` 测试确认。
- **健康/就绪**：用 `/api/v1/health` 做探针。

## 4. 可视化测试（自带控制台，替代低代码平台的简易方案）

1. 起服务（`MOCK_LLM=true` 或真实 key）。
2. 浏览器打开 **`http://<host>:8000/ui`**。
3. 输入业务问题 →「开始分析」，右侧实时看到：目标解析 → 每个工具 ✓/✗ → 最终业务报告；左侧是阶段推进日志。
4. 想验证真实取数：临时把某问题换成"对比各区域营收，识别增长最快的地区"，工具轨迹会显示真实的 `sql_query` 结果行被 Python 读取。
5. 过程回放：`GET /api/v1/debug/traces/<session_id>` 看该次运行每个节点的耗时/token/结果。

> 若团队有内部低代码/Agent 平台（Dify 等），可把 `POST /api/v1/chat/analyze` 按 **OpenAPI 自定义工具** 导入（FastAPI 的 `/openapi.json` 可直接用），把本 Agent 当作"数据分析专家工具"被上层工作流调用——本指南不依赖此路径。

## 4.5 输出脱敏（E4/02，默认开）

- 敏感列（phone/email/id_card/customer_name/身份证/地址…）的值**不进 LLM 上下文**；
  `MASK_LEVEL=sample`（默认）掩值，`strict` 让敏感列彻底不出现（连 `distinct` 都不给，防反推）。
- **CSV 产物不脱敏**（分析师本机要用）——顺序是"先落盘、再脱敏"。
- `MASK_LEVEL=none` 关闭脱敏会**写审计**（`data/audit/masking.jsonl`）；脱敏自身出错时
  **失败即关闭**（丢掉行样本，绝不 fail-open）。
- 与 `SEMANTIC/01` 共用同一份敏感列模式表，避免两处规则漂移。

## 4.6 多数据源（E7/01）

```bash
# 主源：不填 source 时用它（既有行为不变）
DATA_DB_URL=postgresql://user:pw@host:5432/warehouse
# 命名源：JSON 数组或 `name=url` 逗号列表
DATA_SOURCES=[{"name":"crm","url":"postgresql://user:pw@host:5432/crm","dialect":"postgresql"}]
```
- 工具（`sql_query`/`freeform`/`dataset_profile`/`schema_search`）接受可选 `source`；
  未知源名会返回**可读错误并列出可用源**。`GET /api/v1/health` 的 `data_sources` 只回**源名**，不回 DSN。
- 配置写坏（JSON 非法/缺字段）**不阻塞启动**：忽略该条并 warning。
- ⚠ **不做跨源 JOIN / 联邦查询**：需要跨源就在各源分别取数，再用 `python_analysis` 合并。

## 4.7 生产镜像与容器冒烟（E7/01）

```bash
cd web && npm run build && cd ..            # 镜像用预构建的 web/dist
docker build -f Dockerfile.prod -t da-analyst:prod .
./scripts/smoke_container.sh                # build→run→health→analyze→体积；0=通过 2=跳过(无 docker)
```
- 多阶段构建、非 root、带 HEALTHCHECK；**默认不装 sentence-transformers**（torch 会把镜像推到 >2GB，
  检索自动降级 BM25）；需要向量检索：`--build-arg WITH_EMBEDDINGS=1`。
- 冒烟的「跳过」是**独立的退出码 2**：CI 里既不能当通过（假绿），也不能当失败（误报）。

## 4.8 安全（鉴权 / HTTPS / 隔离）

- **鉴权**：应用**无内建鉴权**，必须置于反向代理/网关之后，且只监听 127.0.0.1。
  nginx 最小片段：
  ```nginx
  location / { auth_basic "da"; auth_basic_user_file /etc/nginx/.htpasswd;
               proxy_pass http://127.0.0.1:8000; proxy_read_timeout 300s; }
  ```
  SSE 端点需关闭代理缓冲：`proxy_buffering off;`（否则流式事件会被攒住）。
- **HTTPS**：终止在网关（证书/HTTP2 由网关负责）；应用本身不处理 TLS。
- **多租户**：`DEFAULT_TENANT` 非空时记忆与知识按租户隔离；**数据源层隔离由 DSN 决定**——
  给不同租户配不同的 `DATA_SOURCES`，不要共用同一个高权限 DSN。
- **数据出口**：进 LLM 上下文的样本默认脱敏（E4/02）；但 `GET /analyze/export` 的
  CSV/SQL **保留原始值**，对外分享前需自行确认（交付包 README 已写明）。

## 4.9 起中间件（Redis / PostgreSQL / Milvus）—— 可离线启动

`docker-compose.yml` 里的 5 个镜像 tag 都是**本机已有镜像**，因此在**无外网/镜像源不可达**
的环境也能直接起（这是 2026-09-12 实测确认的：Docker 守护进程正常，但所有镜像源都拉不动）：

```bash
docker compose up -d redis postgres etcd minio milvus
docker compose ps                       # 等 milvus 变成 healthy（首次启动可能要 1~2 分钟）
docker compose up -d app                # app 依赖 redis/milvus 的 healthcheck，不会抢跑
```

要点（都是踩过的）：

- **Milvus Standalone 必须带 etcd + MinIO**，二者不是业务微服务；compose 里已按依赖顺序 + 健康检查串好。
  Milvus 首次启动要建元数据，compose 给了 `start_period: 90s`——**别在它 healthy 前就让 app 连**，
  否则会静默回退 SQLite（知识检索退化成关键词）。
- **MinIO 凭据变量已更名**：`MINIO_ACCESS_KEY/SECRET_KEY` 已废弃（启动日志会告警），
  现用 `MINIO_ROOT_USER/MINIO_ROOT_PASSWORD`。
- **不要给 milvus 配 `9091` 之外的端口**：`19530` 是数据面，`9091` 是健康/指标面（healthcheck 靠它）。
- **启动方式二选一，别混用**：要么用 compose（上面的命令），要么用已存在的 `agent-*` 容器
  （`docker start agent-etcd agent-minio agent-milvus agent-redis`）。
  两者都占 19530/6379，**同时开会端口冲突**。
- **短期记忆 TTL**：`SHORT_TERM_TTL_S`（默认 86400）控制 Redis 里 `da:st:<session>` hash 的
  滑动过期。**不要设 0**（等于永不过期，会话键只增不减）。会话可能停在 `CLARIFY` 等用户回答，
  调太小会在续跑前被回收。

验证（真跑，不是 mock）：

```bash
pytest tests/test_redis_live.py tests/test_milvus_live.py tests/test_pg_live.py -q
# 期望：Redis 2 passed / Milvus 5 passed 1 skipped（skip 的是 Lite 专用断言）/ PG 4 passed
```
