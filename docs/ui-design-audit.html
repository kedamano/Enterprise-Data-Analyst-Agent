总体判断

VERDICT

这套 UI 是合格但匿名的。工程上它是干净的——没有 div 冒充按钮，表格用了真正的 <table>，41 处 aria-label，空态、错误态、加载态都有落地。这些是很多项目做不到的。

但把同一份 brief 交给另一位设计师，大概率会产出几乎一样的页面：shadcn 的令牌脚手架没改过、Aceternity 组件囤了一堆没用、靛蓝到紫罗兰的渐变当主色、系统默认字体栈、内容装进一排排同圆角同阴影的白卡片。这套组合是 2024 年后生成式 SaaS 界面的公共默认值，不是为「企业数据分析」这个题目做的选择。

一句话概括问题所在：它看起来像任何一款 AI SaaS，而不像一台你会把企业账目交托给它、并指望它给出可审计结论的仪器。产品真正的卖点在文案里写着「每条结论都附带工具调用记录与置信度，支持溯源审阅」——而界面没有任何视觉语言在传达「可审计」「可溯源」「有据可查」。这是最值得修改的地方。

设计方向提案

TOKENS

先给方向，再给问题清单——否则后面的每一条修改都会失去共同的目标。方向来自题目本身：一个读取企业数据库、产出带溯源结论的分析系统。它的世界是账本、审计底稿、机构报告、SQL 控制台。

色彩：让颜色只承担语义

核心的取舍是——取消装饰性配色。当前 6 个色系（靛蓝／紫罗兰／天蓝／琥珀／翠绿／玫红）在不同页面代表不同含义，等于没有含义。新方案只保留一个品牌色，其余全部为语义保留：

角色色值唯一用途
纸张 Paper#FFFFFF内容承载面
画布 Canvas#F4F5F3页面底，暖中性灰（替换现有冷灰 #fafbfc）
墨 Ink#14171C正文与标题
品牌 Brand#143A5E机构藏青：主操作、当前上下文、链接
已核验 Verified#1F7A54仅用于「结论已溯源核验」——产品承诺本身
需注意 Attention#9C6412仅用于降级、低置信、需人工复核
失效 Danger#9E2B2B仅用于失败与破坏性操作
界线 Rule#DADCD7分隔线与边框

选机构藏青而非绿或红，有一个本地的现实原因：在中文金融语境里红绿已被涨跌占用，用其中任一色作品牌色都会被误读。藏青是审计机构、年报、监管文件的视觉语言，既不与涨跌冲突，也不落入生成式界面最常选的靛蓝紫罗兰。

字体：一个超家族，两种角色

当前是 ui-sans-serif, system-ui, -apple-system, "Segoe UI"——最默认的系统栈，没有任何性格，且在任何项目上都会得到同样的结果。改为：

用途字族理由
标题 · 正文 · 界面IBM Plex Sans + Noto Sans SCPlex 是为 IBM 技术文档设计的字族，天生带「仪器／技术手册」气质；Noto Sans SC 承接中文，字重与拉丁部分匹配
SQL · 标识符 · 数值 · 度量IBM Plex Mono同超家族、性格明确区分；等宽 + 表格数字，是数据产品必须的

刻意避开 Inter／Geist／JetBrains Mono 这类任何项目都会先想到的选择。Plex 的选择理由是这个题目的实际材料：整个产品界面由数据库标识符、SQL、数字表格、审计记录构成——等宽与表格数字不是装饰，是功能。

字号：六档，不是十八档

令牌字号／行高字重用途
--fs-display32 / 1.16600仅首页主标题
--fs-title22 / 1.25600页面标题
--fs-heading17 / 1.35600区块标题
--fs-body15 / 1.6400正文、报告、表单
--fs-small13 / 1.5400次要说明、表格
--fs-micro11.5 / 1.4500仅单位与元信息

图标同步收敛为三档：16（行内）、20（控件）、24（导航）。当前用了 15 档。

布局：账本，不是卡片墙

这是最大胆也最贴合题目的一条。现在所有东西都被装进同圆角、同阴影的白卡片里——数据库连接、文件、知识库、示例问题，全都长一样。改为：记录之间用发丝线分隔，卡片只保留给真正离散的对象（一个知识库、一个文件夹）。理由直接来自材料：账本用横线分隔条目，不用盒子。当前可删掉约七成盒子。

另一条硬规则：数字列右对齐、使用表格数字。当前报告表格里营收与同比都左对齐，数值无法按量级比对——对一个数据产品来说这是真缺陷。

五条原则

  1. 颜色只承担语义，不做装饰。任何颜色出现时必须能回答「它代表了什么状态」。
  2. 表格是本产品的主要界面形态。优先用行与列，而不是用卡片切碎内容。
  3. 一个比例尺。六档字号、三档图标、七级间距、两种圆角。
  4. 同一动作全程同名。按钮写「导出」，产生的提示就写「已导出」。
  5. 动效只回应操作，不自己发生。

对提案的自我反驳（哪几处我改掉了默认答案）

  • 第一版我选了深松绿作品牌色（呼应会计绿格账本），推翻了——中文金融语境下绿色代表下跌，会被误读。
  • 第一版我打算用奶油底 + 衬线标题 + 陶土橙点缀，推翻了——这正是 brief 点名要避开的默认组合，而且和题目无关。
  • 考虑过深色控制台风格（更「硬核技术」），放弃了：产品的主要产物是一份给人读的审计报告，长时间阅读需要浅底。
  • 「账本而非卡片墙」这条是刻意承担的审美风险。它会牺牲一点「现代 SaaS 感」，换取与本产品承诺（可审计）一致的表达。

P0

报告正文是 text-[14.5px]（Markdown.tsx:16），而其中的表格与代码块降到 text-[13px]。这是用户唯一需要逐行细读、并且要拿去做决策的内容，却比界面里的普通说明文字还小。报告中的数字表格是数据密度最高的区域，13px 加 1.8 行高在这个场景下偏小偏松。

现有报告正文 12.5px 上下文（放大示意）

建议值 15px，行高 1.6

华东增长最快，华北出现下滑。建议复核华北渠道投入产出。
改为：报告正文 15px／行高 1.6（拉丁与中文混排下 1.6 比 1.8 更紧凑而不挤）；表格 14px + font-variant-numeric: tabular-nums。
P1

字体栈没有任何身份信息

index.css 里的字体声明是 ui-sans-serif, system-ui, -apple-system, "Segoe UI", Roboto, "Helvetica Neue", Arial, "PingFang SC", "Microsoft YaHei"——这是操作系统默认字体的完整枚举。它保证了「不会出错」，代价是在任何设备上都长得一样，且与「企业数据分析」没有任何关系。

同一份声明里还定义了 --font-mono 的缺席：全站没有任何等宽字体令牌，SQL 与哈希值用的是 font-mono 默认栈。

改为：IBM Plex Sans + Noto Sans SC + IBM Plex Mono（见方向提案）。

色彩：六个色系，零个语义

P0

同一个颜色在不同页面代表不同含义

全站调用了 6 个色系，但没有一个拥有稳定含义。实测的冲突：

翠绿 = 上传文件 翠绿 = 模型已就绪 翠绿 = 分析已完成 翠绿 = 数据库主机图标
琥珀 = 添加知识 琥珀 = 工具自动调度 琥珀 = 知识库导航
天蓝 = 查看数据源 天蓝 = 全程可追溯 天蓝 = 历史记录导航

首页的三张能力卡（紫罗兰／天蓝／琥珀）与紧随其后的三个快捷按钮（翠绿／琥珀／天蓝）用了重叠但不对应的配色——同一个琥珀色，在卡片上指「工具自动调度」，在按钮上指「添加知识」。用户无法从颜色推断任何事，颜色因此退化为纯装饰。

改为：品牌色承担「主操作／当前上下文」，其余颜色只在表达状态时出现——已核验（绿）、需注意（琥珀）、失效（红）。装饰性用色全部移除。
P1

靛蓝→紫罗兰渐变是生成式界面的公共默认值

主按钮、用户气泡、机器头像三处都用 from-indigo-500 to-violet-600，另有关联的 bg-gradient-to-* 共 11 处。这不是为本题做的选择：它出现在绝大多数同期的 AI 产品里，且 --primary 与 --accent 两个令牌恰好是 indigo-600 与 violet-600——shadcn 默认令牌只换了色相，其余结构（--card／--popover／--muted／--ring）原封未动。

首页还有一处 blur-3xl 的径向光晕（Welcome.tsx:60）作为底部装饰，是典型的「渐变水洗」式装饰。

改为：移除渐变。主操作用单一实色 #143A5E。首页光晕删除——首屏的视觉重心应由标题与内容承担。
P2

圆角：六种取值，相邻档位用量相当

全站 217 处圆角，取值分布为 rounded-lg 80 ／ rounded-full 44 ／ rounded-md 39 ／ rounded-xl 35 ／ rounded-2xl 16 ／ rounded-sm 3。md／lg／xl／2xl 四档用量接近，意味着圆角不表达层级，只是随手选的。

改为：两种——控件 6px、容器 12px，rounded-full 仅保留给状态胶囊。

P2

文件库表格的末列标题是「操作」，但列内没有任何常驻内容——删除按钮仅在 hover 时出现。表头承诺了一列内容，桌面端看不到，触屏上根本触达不到。

结构：装饰当成了信息

P1

示例问题被编号为 1–6，但它们不是序列

首页六个示例问题各带一个 1–6 的方形编号徽标。编号是强结构信号，只在内容确实是序列时才成立（步骤、时间线、流程）。六个互不相关的示例问题之间没有顺序关系，编号制造了并不存在的结构。

改为：去掉编号。示例问题的价值是「看一句、点一句」，垂直列表配一个发送箭头已足够；或改为按主题分组（营收／质量／客户），用真实分类替代假序号。
P1

首屏眉标与主标题内容重复

首页结构是：胶囊眉标「Enterprise Data Analyst Agent」→ 主标题「企业数据分析智能体」→ 说明文案。眉标只是主标题的英文写法，不提供任何新信息，属于 brief 点名的「内容上方多余的排版标签」。同样的模式也出现在每个页面的页头（如「数据源」下方紧跟「智能体可寻址的数据库连接」）。

改为：删除首页眉标。页头副标题只在能说明「这里能做什么」时保留——「智能体可寻址的数据库连接 · 只读访问」中的「只读访问」是有用信息，应保留，「可寻址的」是系统内部说法，应改。
P2

同一说法在首屏出现五次

「六阶段编排」在页头副标题、首屏说明文案、能力卡标题、能力卡描述、底部状态条各出现一次，共五处。每个文案单元应只做一件事。

改为：只在首屏说明文案里讲一次流程；页头副标题改为当前任务上下文；底部状态条只留模型与连接状态。
P2

中圆点连接元信息被反复使用

「数据分析 · 自然语言驱动六阶段编排」「12 个 · 137 分块 · sqlite」「本地用户 · 0 文档 · 0 分块 · 09-15 21:46」「由 DeepSeek 驱动 · 六阶段编排」——用中圆点把不相关信息串成一条，是模板化界面的典型处理，且当每张卡片都这么写时，元信息区变成视觉噪点。

改为：知识库卡片只保留两个真正有决策价值的字段（文档数、最近更新），其余移入详情页。

动效：108 处过渡，一个全局规则

P1

动效分散在每一张卡片上，而不是集中成一次

实测 transition 出现 108 次（约 21 个组件，平均每个 5 处），几乎每张卡片、每个按钮都有 hover 过渡。brief 的判断标准是：散落的效果不如一次编排好的动作——当前正是前者。

同时 animate-spin 出现 22 次，意味着每一个加载态都用旋转图标表达，没有骨架屏。

改为：hover 过渡只保留在「点击后确有跳转或展开」的元素上；表格行、静态卡片的 hover 变化移除。加载态对已知结构的区域（表格、列表、报告）改用骨架屏。保留一次编排动作：分析完成、报告出现时的展开——它回应了用户的操作，且真正值得被强调。
P1

输入框占位文字每 3.5 秒自动轮换

Composer.tsx 用 setInterval 每 3500ms 换一次 placeholder（「分析最近半年的月度销售趋势…」→「诊断数据质量…」）。这是非用户触发的动效，而且作用于正在输入的区域：用户读它到一半、或者正要点进去时它消失了；若用户已开始输入但清空后，它又与刚才读到的内容不同。它不传达任何状态变化。

改为：去掉轮换，用一句固定的、说明能力的占位文字；示例问题已经在首屏承担了「告诉用户能问什么」的职责。
P1

动效降级只覆盖了 5% 的动效

prefers-reduced-motion 在 index.css 中只针对 .da-fade-up 一个类生效（全站唯一一处）。108 处过渡、22 个旋转图标、以及上面那 3.5 秒轮换都不受此设置约束。开启系统「减少动态效果」的用户，看到的界面和普通用户没有区别。

改为：在全局加一条 @media (prefers-reduced-motion: reduce) 归零 duration，并对轮换逻辑加运行时判定。

文案：开发视角泄漏进了用户界面

P1

产品界面直接展示环境变量名

设置页的微信卡片里，用户看到的是这样一段：

真实扫码登录需要已认证的微信开放平台「网站应用」（企业主体 + 认证费用），并在开放平台登记本服务的回调域名。WECHAT_APPID、WECHAT_APPSECRET、WECHAT_REDIRECT_URI 三项配全后生效。

检测到 WECHAT_DEV_SIMULATE=true，可用下方的本地模拟通道跑通扫码登录链路。这不是真实微信授权，仅用于开发调试。

这段内容是写给部署者看的，不是写给使用者看的。WECHAT_DEV_SIMULATE=true 是配置文件的写法，出现在产品界面里等于把运维手册贴在了用户面前。类似问题还有页头的「LLM: real」「Mock 兜底: 关」——real 是代码里的枚举值，「兜底」是内部说法。

改为：面向用户只说两件事——「微信扫码登录当前不可用」+「联系管理员开启」。配置项名称移入开发者文档。状态胶囊改为「模型：正常」／「模型：降级中」。
P2

空态是陈述而不是出口

会话列表空态：「还没有会话 / 在右侧直接提问即可开始」——描述了现状，没有给出可点的动作。知识库卡片空描述：「这个知识库还没有介绍~」——波浪号是仅此一处的非正式标点，与其余文案语气不一致。

改为：空态给一个直接动作（「开始第一次分析」按钮，或直接列三条可点的问题）。空描述改为一致的书面语气，如「暂无说明」。
P2

数值被截断在词中间

数据源页「主数据源」磁贴显示 sample enterpris...——截断位置落在单词中间。数据源名称、DSN 这类标识符应该允许换行或以尾部落位省略，而不是硬截。

改为：标识符用 break-all 或等宽字体下的中部省略；或把主数据源名放到卡片正文而非磁贴标题。

无障碍：焦点环只覆盖了 2 个组件

P0

22 个组件里只有 2 个定义了键盘焦点样式

全站 focus-visible 仅出现在 Composer.tsx（1 处）与 SideRail.tsx（3 处）。其余约 20 个组件的按钮、输入框、可点击行都没有可见焦点环。键盘用户与依赖键盘导航的用户无法知道自己当前在哪一个控件上。同时有 24 个输入框只靠 placeholder 充当标签，缺少持久可见的字段名。

这一项是质量底线，不属于风格偏好。

改为：在 index.css 加全局 :focus-visible 规则（2px 品牌色描边 + 2px 偏移），保证任何可聚焦元素默认可见；输入框补 <label> 或 aria-label。
P1

13 / 17 个 UI 组件从未被引用

src/components/ui/ 下 17 个组件，其中 13 个被引用次数为 0：

animated-tooltip、background-beams、bento-grid、cover、hero-highlight、input、meteors、multi-step-loader、placeholders-and-vanish-input、stateful-button、tabs、text-generate-effect、typewriter-effect

这些是典型的模板组件囤积：流星、光束、打字机、空间网格——它们也正是「看起来像生成式界面」的来源（meteors 等内部使用 #8900ff 之类的高饱和紫，全站 10 处硬编码色主要集中在这些文件）。它们不被引用，但会被打进阅读路径、增加维护面、并在后续开发中被误用。

同时还有两处死代码：index.css 的 .bg-dotgrid 点阵纹理（定义后从未使用）、以及 @custom-variant dark（全站无 .dark 应用点，仅存在于上述未引用组件内部）。

改为：删除这 13 个组件与两处死 CSS。若某个确实要用（例如空态想用 sparkles），再单独引入并纳入令牌体系。

值得保留的部分

KEEP

审查不该只列问题。以下几项在同类项目里属于做得好的，改动时应保住：

  • 语义化 HTML 到位。全站没有 div 冒充按钮的情况，表格用 <table>，41 处 aria-label，破坏性操作有 aria-label 区分目标。
  • 空态、错误态、加载态都有实现，不是空白页。方向是对的，只是文案与呈现方式需要调整。
  • 三栏骨架（导航 56 / 列表 272 / 主区）是适合本产品的结构，密度与信息层级合理，不需要重构。
  • 分析完成后的状态呈现（阶段时间线可折叠、工具调用明细可展开、置信度与溯源可见）确实是产品差异点，应在视觉上被强化而不是弱化。
  • 深色代码块用于 SQL 与 DSN 是正确的选择——标识符需要等宽与视觉区分，只是需要与新的令牌体系对齐色值。
