# 面试稿（STAR · 基于真实项目）

> 适用岗位：AI Agent / 大模型应用 工程师（Python）。
> 项目：Enterprise Data Analyst Agent（企业数据分析 Agent）。
> 原则：**结构与关键词背熟、数字只讲真的**。文末「指标口径卡」里列的都是本次开发可复跑的真数字；凡标【待补】的，先用「量级/趋势」表述，别编精确数。

## 0. 一段话定性（回答「这项目是什么」时先讲这句）

> 这是一个**面向企业数据分析场景的自主 Agent**：用户用一句话提业务问题（比如"最近半年华北营收为什么下滑"），Agent 自主完成 **理解意图 → 发现数据/口径 → 规划 → 真实执行(SQL/Python)→ 分析师解读 → 质检 → 出业务报告** 的闭环。它强调三件事：**结论必须有工具真实结果支撑（不靠模型记忆编数）、可审计可观测、能安全执行代码**。

## 1. 项目整体介绍

### 1.1 一分钟版（约 220 字）

面试官您好。我做的是一个**企业数据分析 Agent**，面向"想拿数据做决策但不会写 SQL/不熟悉口径"的业务同学。用户一句话提问，Agent 用一套**六节点状态机**（理解→规划→执行→分析→质检→报告）自主闭环：规划与拆解交给大模型，**取数交给只读 SQL、分析交给沙箱里的 Python**，每一步工具返回都进结构化追踪，最后质检门禁过了才出报告，结论全部锚定真实工具结果、防止模型编数。技术上我把**规格说明、契约式 Prompt、真实工具、评测回归**做成了一条可审计的链路：含多模型网关与三态熔断、混合检索+重排、分层记忆与检查点、代码沙箱（子进程/Docker 两档）等。您可以从编排、安全沙箱、RAG、评测任意一块切入，我用 STAR 展开。

### 1.2 三分钟完整版（约 600 字）

面试官您好，我来介绍我的项目。背景是：数据分析类岗位的日常大量消耗在"写 SQL、查口径、核对数据质量、写汇报"上；企业里**数据在库里、口径在文档里、模型在聊天里**，三者没打通。市面上通用 Agent 骨架很多，但**真正把"数据分析这个垂直闭环做透 + 做出企业级护栏"的很少**。所以我从 0 自己搭了这个项目，核心矛盾是：**模型爱编数 vs 分析结论必须可信**。

我负责全部设计与实现，交付物包括规格说明书、契约式 Prompt、编排引擎、七个真实工具、评测体系与文档。技术栈是 Python + FastAPI + 自研状态机（不是堆 LangGraph）。

讲四个关键决策：
第一，**编排层**：我用"理解→规划→执行→分析→质检→报告"的**显式六节点状态机 + JSON schema 阶段输出**，而不是让模型自由对话。换来的是：阶段可校验、可回放、可断点续跑；每个阶段输出不合法 JSON 就服务端校验+修复。ReAct 的心智（工具真实结果回灌、Observation 由系统生成）我保留在 Executor 里，但外层用 Plan-and-Execute 保可控。
第二，**工具执行安全**：SQL 只读白名单+行数/超时强制；Python 先做 **AST 模块黑名单**，再在**隔离进程**里跑（还做了 **Docker 档**：`--network none --cap-drop ALL --read-only`，DeepAnalyze 同款隔离清单），危险路径层层防。**模型永远不直接执行**，参数要过 schema 校验，调用全量落审计（脱敏参数、高危标记）。
第三，**"知识 ≠ 数据"**：指标口径、表说明走 RAG（BM25+向量+RRF 混合，含中文二元组），真实数字只允许走 SQL/Python——从 Prompt 约束到工具边界都执行这条，从根上防"用模型记忆代替真实取数"。
第四，**可度量**：我建了 **eval 评测骨架**（golden 用例 + 工具轨迹断言 + 从 trace 读回真 token/成本），并刻意做了 **"防假绿"**：测试强制真实 LLM、禁止静默降级到 Mock，否则判失败。

踩过的大坑后面讲。目前工程面：**离线+沙箱+真实LLM分层测试，最新合并回归 113 passed / 48s**；评测 mock 5 用例 FINISH 率 1.0、平均 4.8 次工具调用。真实 LLM 侧的准确率/成本【待补：充值后跑 `--mode real` 填数】。总结一句：这不是"套个 API 的 demo"，而是一个**把可信、安全、可观测做成默认项**的垂直 Agent。

## 2. 核心模块 STAR（每段约 2.5–3 分钟）

### 2.1 Agent 编排（六节点状态机）

- **S**：数据分析要"可审计、可回放"，而通用框架里模型自由 ReAct 输出难约束、难测试、容易死循环；另一个常见做法"全塞给一个强模型"则不可控、贵。
- **T**：我负责设计编排引擎：一条**显式流水线**，阶段化、可校验、有质量门禁。
- **A**：定 **Context→Planner→Executor→Analyst→Reflection→Reporter** 六个阶段，每个阶段要求模型输出**符合 JSON schema 的结构化结果**，服务端 `model_validate` 校验，不合法就修复/重试；Planner 产出步骤计划（依赖、预期输出、成功判据），Executor 按计划只做**真实工具调用**；Reflection 是**质量门禁**，输出 PASS/REPLAN/FAIL——证据不足就带着失败原因回注 Planner 重规划，且做了 **REPLAN 无进展检测**（同计划+同目标连续两次=空转，提前判失败）。关键权衡：**要可控可测所以选自研状态机而非 LangGraph**，但保留一份等价 LangGraph `build_graph` 便于部署可视化。每一步都有结构化 span + checkpoint，**失败可续跑、过程可回放**。
- **R**：全流程 mock 回归稳定（eval 5 用例 FINISH 率 1.0）；我把"为什么这个设计"落成了代码级事实而不是口述。复盘：下一步补**动态子任务并行**与每阶段 token 预算细分。

### 2.2 代码执行沙箱（SQL 只读 + Python 子进程/Docker）

- **S**：让 Agent 做真分析就要跑代码，但**任意外部代码=灾难**：读库、碰网络、删数据。
- **T**：我负责"让模型产出可执行但**跑不出边界**的代码"。
- **A**：分层防御——① SQL：只读校验（DML/DDL 正则拒绝、单语句）、行数上限、语句级超时（SQLite 用 progress_handler 硬中止、PG 用 statement_timeout）；② Python：先 **AST 扫描拒绝 os/socket/subprocess/requests 等 + `__import__/eval/exec`**，再进 **子进程 `python -I`**（无用户 site、硬超时、产物经会话目录回传）；③ 更进一步做了 **Docker 执行档**：镜像内置 pandas/matplotlib、非 root、`--network none --read-only +tmpfs /work 挂载`，对应"纵深防御而非单点信任"。工具调用全部带**审计记录（脱敏参数+高危标记）**与限流。
- **R**：负路径测试覆盖写入被拒、动态逃逸被拒、超时中止、Docker 断网/只读 rootfs 实测通过（4 条 docker live）。复盘：AST 是"够用的第一道"，真正隔离必须靠容器/子进程，不能只信文本扫描。

### 2.3 混合检索 + 重排（知识 ≠ 数据）

- **S**：指标口径、业务术语在文档里，但检索常"语义对不上字面"（尤其中文、专有名词、编号），单路向量召回不稳。
- **T**：负责知识检索这路：让"找口径"与"取数"分开，检索本身可度量。
- **A**：SQLite/向量双后端，检索走 **Okapi BM25（我加了 CJK 重叠二元组，解决无空格中文整句被当一个词）+ 向量余弦双路召回 → RRF(k=60) 融合 → 短语亲和重排**；可选 cross-encoder 钩子。架构上把"知识(文档口径)"与"数据(真实数值)"用工具边界+Prompt 规则隔离，**知识检索永远不能替代取数**。嵌入加载加了墙钟预算与降级，模型不可用时不阻塞、自动纯 BM25。
- **R**：混合检索有专门单测（BM25/RRF/重排 11 项通过），并且这条链让我修掉一个真实坑（下节讲）。复盘：下一步上文档准入清洗与检索质量分维。

### 2.4 评测与回归体系（防假绿）

- **S**：Agent 项目最大问题不是"能不能跑"，是**改一个 prompt/工具后，质量是变好还是变坏、成本多花多少**——没有评测就只能靠感觉。
- **T**：建一条离线优先的**质量+成本回归线**，让改动可量化。
- **A**：eval 骨架含 golden 用例（`must_find` 关键片段 + `expected_tools` 工具轨迹 + `must_not_appear` 禁止项如退化 SQL"SELECT 1"）；runner 从**结构化 trace 读回真实节点数/工具数/LLM 调用数/token**（不是估算），成本按单价折算；`--mode mock` CI 可跑、`--mode real` 接真实模型。关键设计：**防假绿**——conftest 强制 `MOCK_LLM=false + LLM_NO_FALLBACK=true`，任何测试若静默降级到 Mock 直接失败，杜绝"测试骗自己"。
- **R**：改 schema/编排后跑一轮 mock 回归（最新 113 passed/48s）即可基线对比。复盘：下一版要补检索 vs 忠实度分维和离线-线上一致性。

## 3. 技术难点 STAR（真实踩坑故事，重点练）

### 3.1 嵌入模型加载把整套测试挂死 300s（定位+根治）

- **S**：某天全套离线测试从几十秒变成 >5 分钟仍跑不完，怀疑我新改的检索代码。
- **T**：定位真实瓶颈，别误伤功能。
- **A**：逐段计时定位到 `_embed`：它**每次调用都重建 sentence-transformers（~13s）**，且该库默认会**联网校验**、网络不通时无限阻塞——我原以为是检索逻辑回归，其实是基础设施层卡死。方案：进程级单例缓存 + **墙钟预算**（后台线程加载 + `join(25s)`，超时即禁用嵌入并**降级纯 BM25**），让库/网络问题永远卡不死主流程。
- **R**：套件恢复秒级稳定；顺带印证了我做的 BM25 通道够独立兜底。复盘：基础设施也必须带超时与降级，这是"可运维"的一部分。

### 3.2 中英文 schema 零命中 → 取数退化成 SELECT 1

- **S**：真实 LLM 跑 demo 时发现报告里出现诡异的 `{"1":1}`，且 dataset_profile 报"缺少 table"。
- **T**：为什么真模型会静默拿不到表。
- **A**：定位：真模型把指标解析成**中文"营收"**，而 schema 元数据是**英文列名 revenue**，`schema_search` 关键词零命中返回空表→下游 profile 没表、sql 兜底成 `SELECT 1`。修复：schema_search **零命中回退返回候选表**（带 fallback 标记），参数构造不再退化成空/退化 SQL，并加"禁止出现 SELECT 1"的 eval 断言防复发。
- **R**：修后 run_demo 五工具全 SUCCESS，中文口径场景不再静默退化。复盘：**语言/口径不匹配是真实数据分析 Agent 的高频失败模式**，要用降级策略而不是让失败悄悄发生。

### 3.3 REPLAN 空转（无进展死循环）

- **S**：Reflection 门禁允许 REPLAN，但理论上"证据不足→重规划"可能原地打转，白烧 token。
- **T**：检测并终止空转，但别误杀真的多步任务。
- **A**：加**状态哈希/键无进展检测**：若连续 REPLAN 的计划步骤与 replan 目标完全一致达 2 次，判定无进展，提前 FAIL 并给可解释错误；配合既有步数/重试上限形成多重刹车。用桩驱动整条 driver 验证能在第 N 次空转被切断。
- **R**：专项测试通过；复杂任务仍能跑足步数，不误杀。复盘：Agent 的"防死循环"要**三层**（迭代上限+无进展检测+熔断）。

### 3.4 防"假绿"：静默降级污染测试

- **S**：早期 MockLLM 兜底让服务在无 key 时不崩，但也可能让测试"看似全绿其实在测空壳"。
- **T**：保证绿的不是假绿。
- **A**：conftest 强制 `MOCK_LLM=false` + `LLM_NO_FALLBACK=true`，并给网关加 fallback spy：**发生降级即被记录**，真实 LLM 测试里断言无降级，否则判失败；把"选型/降级"做成可观测事件而不是吞掉。
- **R**：真实 LLM 基线与离线 mock 各司其职，杜绝了"余额扣完测试还绿着"的假象（这点在 3.5 有真实续集）。复盘：**测试的完整性 > 测试的数量**。

### 3.5 一次真实的"上游额度"事故（诚实的失败）

- **S**：用真实 key 跑 `test_agent_real`，网关报 402。
- **T**：区分"我的 bug"与"上游条件"。
- **A**：单步拿到底层错误：OpenRouter 402，明确是"请求 2048 tokens 超当前余额可负担 1049"。这不是代码缺陷（config 注释早已预判 402），于是**不烧余额空跑**，把真实基线留到额度恢复后执行。
- **R**：教训/复盘话术：企业 Agent 必须把**成本配额与 usage 上报**当一等公民——这直接催生了后面"token/成本入 span + eval 实算"的改进。诚实地说：目前真实模型侧的端到端指标是**待补项**，我准备好命令与口径，随时可跑。

## 4. 行为面试（关键词提纲即可）

- **最大挑战**：把"模型爱编数 vs 结论要可信"焊死成系统约束——答案在"知识≠数据 + 工具真执行 + 质检门禁 + 防假绿测试"四条，讲其中 2 条 + 1 个踩坑。
- **技术选型**：自研状态机 vs LangGraph：要**可控、可测试、可回放**→选显式状态机+JSON schema；保留等价 graph 文件降风险。向量库：SQLite/Milvus 双后端按规模切换，默认离线不引重依赖。
- **最自豪的贡献**：不是某个模块，而是**把"可度量"建起来了**：eval + trace 真数字 + 防假绿——它让这个项目能回答"到底有没有用"。
- **若重来**：**更早建评测集**、更早把**多租户与成本配额**当一等需求、更早固定**工具 schema 契约**；总体方向不变。

## 5. 追问预判（准备回答）

| 可能追问 | 应答要点（真实口径） |
|---|---|
| 为什么用 RRF 不用加权？ | 各通道分数不可比（BM25 与余弦），RRF 只看排序，k=60；分数可比才考虑调 α。 |
| 熔断阈值怎么定的？ | 默认 5 次失败/60s 恢复、半开探针 1 个；取自"偶发抖动 vs 持续故障"经验值，**可配置**、时钟可注入便于压测。 |
| 评测集哪来的？ | 自建 golden 5 条（查询/诊断/对比/趋势），断言分**结果片段+工具轨迹+禁止项**；规则见 `app/eval/golden.py`，可扩展。 |
| Mock 会不会让测试失真？ | mock 只用于离线/流程回归，**真实 LLM 套件单独存在且强制 no-fallback**；两类分离。 |
| SQL 只读就一定安全？ | 不只读，还单语句+行数+语句超时+审计；Python 另做 AST+进程/Docker 两层。 |
| 现在最大不足？ | 真实 LLM 端到端指标待补（额度）、动态并行与更细 token 预算、检索质量分维。 |

# 附：v2 增量（Gate-2 收口 · 2026-09-11）

> 本期在 v1（溯源/写码/迭代）之上，用一份 **300 条分析师评测基准**（`docs/测试用例.md`）
> 反查架构，得出的结论是：**缺的不是工具，是分析师的判断力与披露纪律**。
> 下面是可直接讲的三段增量。

## S1｜S（情境）
基准里 83% 是 L2+，40 条 L4 几乎全是**判断陷阱**（辛普森悖论、归因偏误、实验波动、统计检验、
以及"数据有问题也别管，直接给结论"这类对抗性指令）。而我们的 Rubric 权重集中在
**分层/分群/结构效应/口径/分母**——这些在我们的提示词里**一个词都没有**。

## S2｜T（任务）
不是加工具，而是让 Agent 具备**分析师的判断力与披露纪律**，并且**可测**。

## S3｜A（行动）—— 六条线，每条都是"确定性门禁 + 披露"
1. **质量门禁**：把 `dataset_profile` 已算出的**主键唯一性 / join 放大 / 日期连续性 / 粒度**
   接成决策——`BLOCK`（结论必然错，如笛卡尔放大的求和）/`REPLAN`（可补查）/`ANNOTATE`（需披露）。
   **关键设计**：全部规则"有事实 **且** 有主张"才触发——否则样例库那个 52/358 天的稀疏日期会在每个用例上报警。
2. **澄清回路**：模糊请求**反问**而不是 `ERROR` 终止（旧实现在赋值 context 前就 return，问题都拿不到）；
   续跑语义单独设计（否则重跑 Context 会再问一遍 → 死循环），最多反问 3 轮。
3. **口径可比**：期间长度不等 / 比率无分母 / **迭代跨口径比较**（后者直接 REPLAN——那是结论错误）。
   与 E3 联动：迭代轮绕过 Reflection，所以在增量终态单独做检查。
4. **业务语义层**：从维表自动采 `region_id=1 → 华东` 与命名约定外键，注入 context/planner/analyst
   ——**planner 此前完全看不到 schema**，规划 join 全靠猜。
5. **统计严谨 + 对抗性**：`stats_notes`（方法/样本量/显著性）+ 唯一新增的 BLOCK
   `dq_override_silent`——静默顺从"别管数据问题"不是"分析得不够好"，而是**顺从隐瞒已知问题**。
6. **脱敏**：默认开的边界（`sample`/`strict`），单一收口在工具结果进上下文处；
   **CSV 落盘不脱敏**（先落盘再脱敏）；**失败即关闭**——隐私控制不能 fail-open。

## S4｜R（结果）
- 全量回归 **169 → 552 用例、547 passed / 0 failed**；eval mock 基线不变（FINISH 1.0 / 断言 1.0 / 溯源 13/13）。
- 真实放大 SQL 实测：`CROSS JOIN` 5000 行 / 基线 3120 = **1.60×** → BLOCK + 报告披露段。
- 交付物导出（报告+SQL+数据+溯源一次拿走）、多数据源寻址、生产镜像与冒烟脚本。

## 面试可讲的两个"反直觉"点
1. **BLOCK 为什么不直接 FAIL**：放大后的结论**可补救**——把缺口喂给 planner 通常一次修对；
   直接失败等于放弃机会。但额度用尽时必须 FAILED，绝不降级成"看起来正常"的 best-effort 报告。
2. **我自己踩了三次同类坑**（PII 跳过因导入深度写错而静默失效、`AnalysisResult` 静默丢字段、
   转义把字符串写坏）——**每一次都是被自己写的门禁用例抓住的**。
   这恰好证明这套门禁在起作用，也是"防假绿"从口号变成机制的证据。
